## 3. データ

### 3.1 第1段（いま使えるデータ）

- **出典**：GitHub の公開リポジトリ [komo135/forex-historical-data](https://github.com/komo135/forex-historical-data)
  （コミット `e6f76e71ab8cc78d7e7e7fd9c54eb42e5cd9ed9d`）の1時間足 CSV（`<銘柄>/<銘柄>h1.csv`）。
  - リポジトリにあるのはちょうどこの12銘柄で、選り分けはしていない：
    EURUSD・GBPUSD・USDJPY・EURJPY・GBPJPY・AUDUSD・USDCAD・AUDJPY・XAUUSD・EURGBP・EURCHF・USDCHF。
  - 列は `Date,open,high,low,close,tick_volume` で、MetaTrader5 の Python パッケージの `copy_rates` の出力と同じ名前。
    週の構造（土日の足がなく、週は月曜0時に始まる）も MT5 のブローカーのデータと合う。このことから、MT5 のブローカーのデータを書き出したものと推定する。
    価格が整数（例：EURUSD の 1.27801 が 127801）なのは MT5 の形式ではなく、公開者の後処理と見られる。ブローカーは不明（出どころを確かめられない、という制約を結果にも書く）。
  - 各銘柄 57,600本。最終の足は 2022-03-04 23:00。始まりは 2012-11-15〜16（EURCHF は 2012-10-30、XAUUSD は 2012-05-17）。
- **ほかの出典を使わなかった理由**
  - histdata.com・Dukascopy・Yahoo Finance・Hugging Face・Google ドライブ・Kaggle は、この環境からの接続がプロキシに拒否された（2026-10-31）。
  - philipperemy/FX-1-Minute-Data（コミット `e0e0e9a3f368b745a0631f2375055da32aff97f7`）は、データ本体が Google ドライブと histdata.com にあり、取得できなかった。
  - asiertrades/HISDATA-EURUSD（コミット `7057b9fd5cc1797cb551b70929b93ffdd2945436`）は EURUSD だけで、検出力にほとんど寄与しない。
- **時刻の基準（確かめたメタデータ。時刻の列だけを見た）**
  - 2015〜2022年の FX 11銘柄では、金曜の最後の足は、通常の週は23時台（約346週）、米国と欧州の夏時間がずれる週だけ22時台（24週中23〜24週）。
    週は、どちらの週も月曜0時に始まる（ずれる週は、週の最初の1時間にあたる日曜23時の足がない）。
  - これは、欧州の夏時間に連動する GMT+2/+3 のサーバー時計の特徴である（通常の週は NY＋7 と同じで、ずれる週だけ NY＋6 になる）。
  - よって komo135 の時刻は、欧州の夏時間の規則（tz 名 `Europe/Athens`）で UTC に戻し、`fusion.data.utc_to_server` で NY＋7 に換算する。
    通常の週の時刻は変わらず、ずれる週の足だけが1時間後ろにずれる。夏時間の切り替え（日曜 01:00 UTC）は市場が閉まっている時間なので、足の重なりや抜けは起きない。
  - 2013〜2014年は、通常の週も金曜22時台で引ける週が多い（ブローカーの引けが早かったと見られる）。どちらも U-X（参考）の期間で、全決済は足の確定22時で発動するので週末はまたがない。
- **週末・暦の休場以外で12時間以上空いたところ**（休場明けフォールバック GAP_FALLBACK の対象）
  - U-D：XAUUSD の 2021-12-23 23:00 → 12-27 01:00。12/24 に金の足がなく、暦では 12/24 は休場日ではなく早仕舞いの日なので、木曜には全決済が立たない。建玉があれば GAP_FALLBACK で決済される（XAUUSD なので警告の件数には入らない）。
    ほかは年末年始（2020-12-24〜28、2020-12-31〜2021-01-04）と Good Friday（2021-04-01〜05）で、どれも窓の前に暦の全決済が立つ。
  - U-X：USDCHF 2015-01-15 20:00 → 01-19 00:00、EURCHF 2014-12-31 19:00 → 2015-01-19 00:00（1月1〜18日がない。スイス国立銀行の下限撤廃 1月15日を含む）、
    EURCHF 2015-03-23 23:00 → 03-25 03:00、GBPJPY 2017-08-14 01:00 → 15:00、ほかに年末年始。
- **変換**（この順で行う）
  1. 価格＝round(生の値) ÷ 10^桁（読んだ直後に整数へ丸める。生の値に 127801.00000000001 のような浮動小数の端数があるため）。
     桁は、円のペア（USDJPY・EURJPY・GBPJPY・AUDJPY）が3、XAUUSD が2、ほかは5。この時点で、すべての価格 x が |x·10^桁 − round(x·10^桁)| < 1e−6 を満たすことを確かめる。
  2. 時刻を上の規則で NY＋7 に換算する。
  3. 換算後の時刻で土日の足を除き、同じ時刻の足は最初のものを使う（`fusion.data` と同じ処理）。これ以外の修正はしない。
  4. 書き出しの価格は Bid とみなし、四本値すべてに s_nom/2 を足して、水準を仲値にそろえる。
     これは水準をそろえるだけの処理で、R には影響しない（開発データで、取引と R が一致することを確認済み）。可変スプレッドは扱えない（v1.0 と同じ近似）。
- **スプレッド（s_nom）**：SPEC §10.3 の表の値。表にない3銘柄は、評価の前に次の値で固定する。
  - EURGBP 0.00015、USDCHF 0.00015、EURCHF 0.00020（SPEC の表の主要ペアと同じ水準の、個人向けの標準的なスプレッド）。

### 3.2 第2段（利用者の MT5 のデータ。第1段で打ち切りにならなかったときだけ）

**書き出しの前に決めること（利用者に確かめて記録する）**
1. **接触の申告**：§2 の確認を、2022-03-05〜2026-10-31 についても行う。扱いは §2 と同じ。
2. **銘柄の対応表**：ブローカーの銘柄一覧から、12銘柄への対応を作る。
   - 接尾辞・接頭辞（EURUSD.a、m.EURUSD など）は取り除いて読む。
   - 同じ銘柄に口座種別が複数あるときは、標準口座のものを選ぶ。
   - 金はドル建て（GOLD、XAUUSD など）だけを XAUUSD とする。円建ての金は使わない。
   - 対応する銘柄がないものは除き、理由を記録する。
3. **記録**：ブローカー名・サーバー名・口座の種別（デモか本番か）・書き出した日。

**書き出し**：対応表のすべての銘柄の1時間足を、MT5 の「表示」→「銘柄」→「チャートバー」で書き出す。
- 銘柄を選び、時間足を H1、開始を 2021-12-01 にして「リクエスト」で履歴を取り、「バーをエクスポート」で保存する。
- ファイル名は `<12銘柄の名前>_H1.csv`（例：`USDJPY_H1.csv`）。形式は MT5 の既定（タブ区切りの `<DATE> <TIME> <OPEN> …`）のままでよい。
- 書き出したファイルはコミットしない。ファイル名・行数・期間・SHA-256 を結果に書く。

**使い方**（評価の前に固定する）
- **読み込みの順序**：土日を含む生の時刻のまま読み、時刻の判定と換算をしてから、換算後の時刻で土日の足を除き、同じ時刻の足は最初のものを使う
  （`fusion/mt5_parity.py` の `read_bars` と同じ順序。`fusion.data.load_mt5_csv` は換算の前に土日の足を除いてしまうので使わない）。
- **時刻の判定**：FX の銘柄（XAUUSD 以外）の生の時刻で判定し、XAUUSD にも同じ換算を使う。
  - 12/24〜1/3 を含む週、足が100本未満の週は除く。残りの各週について、週の最後の足（時差によっては土曜の朝になる）の開始時刻＋1時間を、
    その週の金曜 17:00 ニューヨーク時間（を UTC にしたもの）と比べ、その週のサーバーの UTC からの時差 o_w（時間）を求める。
  - 次の仮説のうち、週の95%以上で o_w が一致するものを採る。
    ① 米国の夏時間に連動する NY＋7（o_w＝NY の UTC 時差＋7）→ そのまま使う。
    ② 欧州の夏時間に連動する GMT+2/+3（o_w＝`Europe/Athens` の UTC 時差）→ `Europe/Athens` で UTC に戻し、`utc_to_server` で換算する。
    ③ 一定の時差 h（o_w が h で一定。UTC なら0、JST なら9）→ その時差で UTC に戻し、`utc_to_server` で換算する。
  - ①と②の両方が当てはまる（米欧のずれる週がない）ときは①とする。どれにも当たらないときは、U-E は「未決」とする（評価の後で換算を決めることはしない）。
- **期間**：換算後の時刻で 2021-12-01 00:00 〜 2026-10-31 23:00 の足だけを使う（それより前・後の足は、走らせる前に捨てる）。
  - エントリーを数えるのは 2022-03-05 00:00 〜 2026-10-31 23:00。
  - 系列の最初の足が 2021-12-01 より後の銘柄は、「最初の足＋3か月」からエントリーを数える。最初の足が 2023-01-01 より後の銘柄は除く。
  - U-E は komo135 とは別の系列として、銘柄ごとに1本で走らせる（つなぎ合わせない）。
- **価格**：Bid とみなし、第1段と同じく s_nom/2 を足す。
- **暦**：SPEC §2.6 の既定だけを使う。ブローカー固有の休場は足さず、GAP_FALLBACK の件数として報告する。
- **不備**：四本値の矛盾は件数を報告するだけで、直さない。
- **最低限の量**：接触の申告で除いた銘柄×期間を除いた後で、使える銘柄が8つ以上、かつ U-E の合計が30銘柄年以上。
  銘柄年は、銘柄ごとにエントリーを数える期間の日数÷365.25 を足したもの。満たさなければ第2段は行わず「未決」とする。

## 6. 素朴ベースライン（第2段だけ）

- v1.0 の事前登録 §5 と同じ（同じループ・同じ時刻ルール・同じ出口、確率 p で次の足の始値に成行、SL＝1.5ATR）。違うところは次のとおり。
- **乱数**：`numpy.random.default_rng(seed * 1000 + 番号)`。seed＝0〜19。系列は先頭（komo135 は各銘柄の最初の足、利用者の系列は換算後の 2021-12-01 以降の最初の足）から走らせる。
  - komo135 の系列の番号は次の順で 0〜11：EURUSD, GBPUSD, EURJPY, AUDUSD, USDCAD, AUDJPY, XAUUSD（ここまで v1.0 と同じ番号）, USDJPY, GBPJPY, EURGBP, EURCHF, USDCHF。
  - 利用者の MT5 の系列は、同じ順の番号＋100（100〜111。同じ乱数列を別の系列に当てないため）。
- **p の格子**：{0.005, 0.0075, 0.01, 0.0125, 0.015, 0.02, 0.03, 0.05, 0.08}（v1.0 の格子に 0.0075 と 0.0125 を足した）。
- **p の決め方**：損益は見ず、回数だけで決める。判定プール（U-D＋U-E）での20シードの取引数の平均が、v1.1 の判定プールの取引数に最も近いもの。
  ±20% に入らなかった場合は、そのことを報告する。

## 7. 段階と打ち切り

1. **第1段（いま）**：§2 の利用者への確認を記録してから、komo135 のデータで、素朴ベースライン以外の構成を1回だけ走らせる。
   - **打ち切り**：v1.1 の U-D の平均R ≤ 0 なら、v1.1 は「不合格（第1段で打ち切り）」と記録し、第2段は行わない。
   - **継続**：U-D の平均R＞0 なら、利用者に第2段のデータを依頼する。
   - **第1段で出すもの**：構成ごとの U-D と U-X（参考）の取引数・平均R・標準誤差、§9 のデータ源の照合、切断テストの一致だけ。
     P1〜P6 の表・素朴ベースライン・PSR は出さない（スクリプトは第1段では計算もしない）。
   - 第1段の値は途中経過であり、優位性の証拠としては使わない。
2. **第2段**：§3.2 の手順で利用者のデータを受け取ったら、1回だけ走らせ、判定プール（U-D＋U-E）で §9 の P1〜P6 を判定する。
   - 第1段と同じコミットのコードで走らせる。コードを直してよいのは、結果のファイルができる前の技術的な失敗（例外・読み込みの失敗）だけで、
     取引の集合が変わる変更はしない。直した場合は、開発データのゴールデン（`fusion/tests/golden/`）と、第1段の U-D の v1.1 の取引一覧が全件一致することを確かめてから、全構成を走らせ直す。
     合否は走らせ直した結果で出し、第1段と差があれば逸脱として記録する。
   - **期限**：2027-02-01 までに第2段を行えなければ、v1.1 は「未決」のまま閉じる。自動売買は無効のまま。
   - 「未決」は「検証していない」という意味で、優位性があるという意味ではない。

## 8. 統計の定義（v1.0 の事前登録 §6 と同じ。違うところだけ書く）

- **R・平均R・t値**：v1.0 と同じ（`fusion/broker.py` の `pnl_r`、t＝平均÷(標準偏差÷√n)、ddof=1）。
- **月ブロック・ブートストラップ**：v1.0 と同じ（10,000回、seed=12345）。抽出する月は、判定プールで取引が1回以上ある暦月（v1.0 の `month_block_ci` と同じ）。プールの別は問わない。
- **P6 の PSR**（Probabilistic Sharpe Ratio）：PSR＝Φ( SR̂·√(T−1) ÷ √(1 − γ₃·SR̂ + (γ₄−1)/4·SR̂²) )。v1.0 の DSR の式で SR₀＝0 としたもの。
  - 系列：判定プールの月次R（その月の全取引の pnl_r の合計。取引のない月は0）。期間は 2020-05 から 2026-10 までの各月。
  - SR̂＝月次Rの平均÷標準偏差（ddof=1、年率化しない）。T＝月数。γ₃＝歪度、γ₄＝尖度（正規分布で3になる定義）。v1.0 の V（試行の SR の分散）と N は使わない。
  - 理由：v1.0 の P6（N＝250）は、同じ系統のデータで約250の構成を試したことへの割り引きだった。v1.1 の判定プール（U-D・U-E）は、
    F+h1trans を選んだデータと期間が重ならないので、選択の偏りは新しいデータそのものが取り除く。もう一度試行回数で割り引くと二重になる。
    （U-X は期間が重なるので、この理由が当てはまらない。だから判定に使わない。）
  - これは v1.0 の P6 からの緩和で、歪度・尖度の補正を除けば P1 とほぼ重なる基準になる。独立の関門としての役割は小さい。

## 9. 合格基準（第2段の判定プール U-D＋U-E。P1〜P6 をすべて満たしたら「合格」）

| # | 基準 |
|---|---|
| P1 | 判定プールの平均R＞0、t≥2.0、月ブロック・ブートストラップの95%区間の下限＞0 |
| P2 | U-D と U-E の両方で平均R＞0。かつ、判定プールで30回以上取引した銘柄のうち60%以上で平均R＞0 |
| P3 | U-D と U-E をそれぞれ期間の中点で前半と後半に分け、前半どうし・後半どうしを合算して、どちらも平均R＞0。中点は U-D＝2021-04-09 12:00、U-E＝2024-07-03 00:00 |
| P4 | v1.1 の平均R ≥ 素朴ベースライン（20シードの平均R の平均）＋0.10R。かつ、20シードの平均R の95パーセンタイルを上回る |
| P5 | Rの上位1%の取引（ceil(0.01·n) 件）を除いても、判定プールの平均R ≥ 0 |
| P6 | PSR ≥ 0.95 |

- 取引が0回のプールは平均Rが求まらないので、P2 を満たさない。30回未満の銘柄は、P2 の銘柄の割合の分母に入れない。
- **警告**（不合格ではないが、自動売買の前に解消が必要）：v1.0 と同じ3つ。FX は XAUUSD 以外の11銘柄。
  - 売買の片方だけがマイナス。GAP_FALLBACK が FX で年1件を超える。EURUSD の10か月あたりの回数が15回未満
    （v1.1 は fusion より取引が少なく、v1.0 の最終検証では約17回だった。偶然に出ることがある）。
- **参考として報告するもの**（合否に使わない）：
  - U-X（2015-01-15 を含む CHF の取引を除いた値と、含めた値）、U-E後
  - fusion（v1.0）の同じプールでの成績、v1.1 − fusion の差と標準誤差
  - スプレッド前提を1.5倍にした v1.1
  - 銘柄別・プール別・年別・決済理由別、上位1%を除いた値、GAP_FALLBACK の件数
  - **データ源の照合**（第1段から）：使用済み7銘柄の 2018-01-01〜2020-05-14 について、komo135 版で走らせた fusion の取引と、
    v1.0 の OANDA 版の取引（`fusion/results/final_eval_trades_main.csv.gz` の U-B）を比べ、件数・エントリー（銘柄・方向・時刻）の一致率・平均R を報告する。
    この期間の成績は v1.0 で公開済みなので、新しい成績の情報は含まない。出どころ不明のデータが同じ取引を生むかを確かめるためのもの。

## 10. 検出力（結果を見る前の見込み）

前提：v1.1 の1取引あたりの R の標準偏差 2.15（v1.0 の最終検証の F+h1trans）、取引の頻度 21.5回／銘柄年。

| | 銘柄年 | 取引数（見込み） | 平均Rの標準誤差 | t≥2 に要る平均R |
|---|---|---|---|---|
| 第1段の打ち切り（U-D） | 21.7 | 約465 | 0.100 | — |
| 第2段の判定（U-D＋U-E。12銘柄を 2026-10 まで書き出せた場合 U-E 55.9） | 77.6 | 約1,670 | 0.053 | +0.105 |

| 真の平均R | 第1段で打ち切りになる確率 | 第2段の P1（t≥2）を満たす確率 | 第2段の P4 を満たす確率 |
|---|---|---|---|
| 0 | 50% | 2% | 1% |
| +0.05 | 31% | 15% | 10% |
| +0.10 | 16% | 46% | 36% |
| +0.15 | 7% | 80% | 72% |

- 実質的な関門は P4（素朴ベースラインを 0.10R 上回る）と P5（上位1%を除いても0以上）。
  v1.0 の F+h1trans は、上位1%を除くと −0.013R だった。同じ分布なら、P5 も平均 +0.12R 前後を要求する。
- 表の確率は、打ち切りを通ったことを条件にしない値。打ち切りと P4・P5 を合わせると、合格の確率はさらに下がる。
  v1.1 に +0.10R の実力があっても、合格の確率は3割に届かない見込み。
- 表は、素朴ベースラインの平均を +0.019R（v1.0）の定数とみなし、P4 の95パーセンタイルの条件を無視している。
- 頻度と標準偏差は v1.0 の7銘柄の値。EURGBP・EURCHF・USDCHF は値動きが小さく、R の範囲（R09・R10）や SL バッファの下限 3×s_nom の効き方が違うので、取引数は表より少なくなりうる。
- 12銘柄は約6通貨から作られているので、銘柄間で取引の結果が相関する。実効的な取引数は表より少なく、検出力は表より低い（P1 の月ブロック区間がこの相関を一部取り込む）。
- 不合格は「優位性がないことの証明」ではない。とくに +0.05R 前後の小さな優位性は、この量のデータでは見分けられない。

## 11. 判定後の扱い

- **第1段で打ち切り、第2段で不合格、または未決**：v1.1 は「実データで優位性を確認できなかった」（未決なら「未検証」）と記録する。EA の自動売買は無効のまま。
  - 同じデータで別の改良案を選び直すことはしない。次の案は、さらに新しいデータ（例：2026年11月以降の実時間のデータ）で評価する。
- **第2段で合格**：次の順に進める。どれかで止まったら、自動売買は有効にしない。
  1. v1.1 の仕様を、SPEC 本文を変えずに追補（`fusion/SPEC_v1_1.md`）に書く（R13 の評価順＝R12 の次、T_SMALL＝SMALL 帳簿の持続型ダウ状態、既定 ON）。
  2. EA を対応させる：入力（例 `InpH1Transition`）、RC_R13 の判定、`_info.csv` の switches への出力、パネルと README の表。
     s_nom の表（`FE_SpreadTable`）に EURGBP・USDCHF・EURCHF を足す。
  3. 照合の道具を対応させる：`fusion/mt5_parity.py` の switches と構成名、`mt5/engine_check` の pyref・transpile。
     開発期間で Python と完全に一致することを確かめる（Python の判定 `F+h1trans` は変えない）。
  4. 利用者の MT5 のストラテジーテスターで 2022-03-05 以降を回し、照合ハーネスで Python と一致することを確かめる（SPEC §18 の基準）。
     開始日の前に H1 が10,000本以上あること、固定スプレッド、`InpLogsCommon=true`、Python は EA の `_bars.csv` の先頭から回す（`mt5/README_FUSION.md` の照合手順）。
  5. デモ口座で3か月、通知のみで動かし、30シグナル以上で Python との一致を確かめる。監視は対応表の銘柄すべて（v1.1 の頻度では、銘柄が少ないと3か月で30シグナルに届かない）。
  6. そのうえで、自動売買を任意で有効にできる（risk 0.5% から）。

## 12. 実装の約束

- `fusion/strategy.py`・`fusion/broker.py`・`fusion/final_eval.py` は変えない（v1.0 の再現とテストを壊さないため）。
- `fusion/v11_eval.py` が、12銘柄の一覧・FX の一覧（11銘柄）・プール名と期間・価格の桁・3銘柄の s_nom・乱数の番号を持つ。

  - 利用者の系列の素朴ベースラインは、仕事ごとに `SYMBOL_ORDER` を「100個の空き＋12銘柄」に差し替えて走らせ、終わったら元に戻す。
  - スプレッドを1.5倍にする構成は、仕事ごとに s_nom を差し替えて走らせ、終わったら必ず元に戻す。
- `fusion/final_eval.py` から使うのは、モジュールの定数に頼らない関数（`summary`・`month_block_ci`・`monthly_r`・`sharpe`・`moments`・`deflated_sharpe`・`drop_top`・`judge_p1`・`judge_p3`・`judge_p5`）だけ。
