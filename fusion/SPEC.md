## 0. 結論と判断の記録

### 0.1 一言で
4H レベルの上昇（下降）構造の中で、押し（戻り）が 4H MA（1H 足の SMA80）に届き、その 4H MA が逆向きでないときに、1H レベルで「安値切上げを保ったまま戻り高値を上抜ける」瞬間を逆指値で取る。

- **損切り**：切上げ安値の外に置く。
- **出口**：「4H レベルの新しい押し安値が確定するたびに損切りを引き上げる」と「週末・休場の前に全決済」の 2 つだけ。分割・建値移動・固定利確・時間決済はしない。
- **日足・反対勢力・節目**：既定では売買を止めない。スコアと理由コードで表示し、事前登録したアブレーションで効果を測る。

## 2. データ・時刻・先読み禁止の約束

### 2.1 入力
- H1 OHLC を使う。サーバー時間＝NY時間＋7時間（NY クローズ 17:00＝00:00、GMT+2/+3、米夏時間連動）。
- 読込時に、サーバー時間の土日に入った足を除く（`fusion/data.py` の `drop_weekend`）。ティックのない時間の足は作らない。

### 2.2 確定足と約定
- 判定はすべて確定足の終値で行う。足 t の確定時刻＝開始時刻＋1時間。
- 発注は足 t の確定時に行い、約定は足 t+1 以降とする。損切りの変更は次の足から有効。

### 2.3 スイングの認識時刻
足 j のスイングは、足 j+N の確定時に初めて認識する（認識時刻＝スイング足＋N本）。時刻 t で使えるのは j ≤ t−N のものだけ。

### 2.4 上位足
- H4・D1 の足そのものは使わない。上位足は、期間を換算した MA とスイングの深さで表す（4H の20MA＝SMA80、4H レベルの波＝深さ12、日足の20MA＝SMA480、日足レベルの波＝深さ72）。
- 上位足の未確定足を参照する余地はない。
- 節目（水平線）は、t 時点で認識済みのスイングだけから毎回作り直す（§6.2）。

### 2.5 単一時間足の利点
- H1 足の集合は、ブローカーの時差（GMT±）に依存しない。1時間ごとの区切りは同じで、ラベルが変わるだけである。
- 時差が影響するのは §2.6 の時刻ルールの換算だけで、指標・スイング・判定は一致する。
- H4/D1 を再集計しないので、日曜足や区切り差による Python と MQL5 の食い違いが設計上起きない。

### 2.6 時刻ルール
- 時刻はサーバー時間。hc＝足の確定時刻の「時」で、翌日0:00の確定は24とする。M15 では分を小数にする（例：22:45→22.75）。日付＝足の開始日。
- 優先順位は表の上から。

| 区分 | 条件 | 新規・待機注文 | 建玉 |
|---|---|---|---|
| 休場日 | 日付が CAL_CLOSED | 一切置かない | その日の最初の足の確定で全決済 |
| 早仕舞い日 | 日付が CAL_EARLY | hc≥17 で取消し、新規なし | hc≥19 の足の終値で全決済 |
| 週末前・休場前日 | 金曜、または翌平日が CAL_CLOSED | hc≥20 で取消し、新規なし | hc≥22 の足の終値で全決済（WEEKEND） |
| ロールオーバー | hc≥23 または hc<1 | 取消し、新規なし（23:00〜01:00 は注文が存在しない） | 保有を続ける |
| 休場明け | 前の足の確定から次の足の始まりまで12時間以上空いた | 約定判定の前に取消す | その足の始値で全決済（GAP_FALLBACK。件数を記録して報告する） |

- **CAL_CLOSED**（既定）：12/25、1/1。XAUUSD は Good Friday（復活祭の2日前、付録C）を加える。
- **CAL_EARLY**（既定）：12/24、12/31。XAUUSD は米感謝祭（11月第4木曜）の翌金曜と、米独立記念日（土曜なら前日、日曜なら翌日）を加える。
- ブローカー固有の休場・早仕舞いは入力リストで追加する。Python と MQL5 には同じリストを渡す。
- **根拠**：OANDA の IS では FX の 12/24・12/31 が 21:00 で終わる。XAUUSD は Good Friday が休場で、感謝祭翌日・独立記念日は 20〜21時で終わる。MinCore では祝日週の6件が休場をまたいで持ち越していた。

### 2.7 判定開始（ウォームアップ）
- ATR14[t]、SMA80[t]、SMA80[t−12] が計算済みで、かつ t≥92 の足から評価する。BIG 帳簿の高値・安値が2個ずつそろうまでは R01 とする。
- SMA480、D1 帳簿、D1 状態が未計算の間は、それを使う情報項目を「不明」と表示し、スコアは中立値にする（S4=10、S6 の乖離部分=8）。
- MT5 では、評価開始前に H1 で10000本以上の履歴を用意する（D1 帳簿が8000本を使うため）。

## 3. 指標（すべて H1 足）
```
SMA_n[t]   = mean(C[t-n+1 .. t])                          # iMA(MODE_SMA, PRICE_CLOSE)
TR[t]      = max(H[t], C[t-1]) - min(L[t], C[t-1]);  ATR[t] = mean(TR[t-13 .. t])   # iATR(14)
slope80[t] = (SMA80[t] - SMA80[t-12]) / ATR[t] * d        # 4H MA の向き（12本＝4H 足3本）
gap[t]     = (SMA80[t] - SMA480[t]) * d / ATR[t]          # 4H MA と日足 MA の乖離（ATR_H1 単位。1.5×ATR_D1 ≒ 8.4×ATR_H1）
conv(W)    = min_{k∈W} |SMA20[k] - SMA80[k]| / ATR[k]     # 1H MA と 4H MA の収束の度合い
```

## 4. スイング帳簿
```
isHigh(j, N): H[j] >  H[j+k] (k=1..N, 新しい側は厳密に高い) かつ H[j] >= H[j-k] (k=1..N, 古い側は以上)
isLow (j, N): L[j] <  L[j+k] かつ L[j] <= L[j-k]
帳簿     深さN  探索範囲LB   用途
SMALL      3      400       1H レベル：トリガー（戻り高値 SH、直前安値 L0）
BIG       12     3000       4H レベル：環境（G1）、構造トレール、節目候補
D1        72     8000       日足レベル：情報（日足状態）、節目候補、パターン③
book.highs(t, k) = 確定済みのスイング高値 j のうち max(t-LB+2, N+1) <= j <= t-N を満たすものを、新しい順に最大 k 個
```
`fusion/indicators.py` の `pivots` と `SwingBook`、MQL5 の `FindSwingHighs/Lows` と不等号・範囲が一致する。MQL5 では、新しい確定足ごとに足 j=t−N だけを判定して帳簿に追加する増分方式で実装する（全走査は重い）。

## 5. 環境認識

### 5.1 G1：4H レベルのダウ構造（既定のゲート）［共通 C01］
```
BH = BIG.highs(t,2), BL = BIG.lows(t,2)   （各2個そろわなければ R01）
買い: BH[0].p > BH[1].p かつ BL[0].p > BL[1].p かつ C[t] > BL[0].p   → j_peak = BH[0].idx（押しの起点）
売り: BL[0].p < BL[1].p かつ BH[0].p < BH[1].p かつ C[t] < BH[0].p   → j_peak = BL[0].idx
```
- 「終了≠転換」は次のように表れる。
  - HH&HL でも終値が押し安値 BL[0] 以下なら、上昇は「終了」で UP 扱いしない。
  - LH が出ただけなら NEUTRAL。
  - 反対側の LH&LL が確定して初めて DOWN になる。
- 買いと売りは排他で、同時には成立しない。

### 5.2 MA 傾きゲート（既定のゲート）［共通 C05／賢人 X15・K02／100億本人「80MA の方向」］
slope80[t] ≥ SLOPE_MIN（=0。4H MA が最低でも水平）。満たさなければ R08。

### 5.3 持続型ダウ状態機械（表示・スコア・アブレーション用）［共通 C01、案1］
SMALL・BIG・D1 の各帳簿について、確定足 k の昇順に次を回す。状態 T∈{+1,0,−1} と END（終了の兆し）を持つ。
```
初期: T=0, PLi=PHi=-1, X=NaN, END=0, SH=[], SL=[], used_h={}, used_l={}
for k = 0, 1, 2, ...:
  j = k - N
  if j >= N:
    if isHigh(j,N): SH.append(j); if T==+1 and PLi>=0 and j>PLi and H[j] < X: END=1      # 上昇中の高値切下げ
    if isLow(j,N):  SL.append(j); if T==-1 and PHi>=0 and j>PHi and L[j] > X: END=1      # 下降中の安値切上げ
  if SH and SH[-1] not in used_h and C[k] > H[SH[-1]]:                                  # 直近確定高値の初回終値上抜け
    h = SH[-1]; used_h.add(h); a = argmin_{h<i<=k} L[i]（最初の最小）; b = SL のうち idx<h の最新
    if b があり L[a] > L[b]: T=+1; PLi=a; X=max(H[a..k]); END=0                          # 安値切上げ＋高値更新＝上昇確定（転換または継続）
    elif T==-1:             T=0;  END=0                                                 # 下降の「終了」（転換ではない）
  if SL and SL[-1] not in used_l and C[k] < L[SL[-1]]:                                  # 下抜け（対称）
    l = SL[-1]; used_l.add(l); a = argmax_{l<i<=k} H[i]; b = SH のうち idx<l の最新
    if b があり H[a] < H[b]: T=-1; PHi=a; X=min(L[a..k]); END=0
    elif T==+1:             T=0;  END=0
  if T==+1: X = max(X, H[k]);  if T==-1: X = min(X, L[k])
  記録: T[k], END[k]
```
- 同じ足で上抜けと下抜けが成立した場合は、上抜け→下抜けの順に処理する。
- 状態は、最初の「切上げ＋更新」または「切下げ＋更新」の後は初期値に依存しない。MQL5 では OnInit で履歴の先頭から再生する。
- 表示上の呼び方：T_D1（日足）、T_BIG（4H）、T_SMALL（1H）。

### 5.4 日足との関係と戦争状態［共通 C12／D01（2値で決め打ちしない）］

## 6. 場所（押し目・戻り目の位置と節目）

### 6.1 G2：押しが 4H MA に届いた（既定のゲート）［共通 C02・C05］
```
W = (j_peak, t]（確定足のみ）
depth = min_{k∈W} (L[k] - SMA80[k]) / ATR[k]      （売り: min_{k∈W} (SMA80[k] - H[k]) / ATR[k]）
G2: depth <= ZONE_ATR (0.5)                          満たさなければ R02
```

### 6.2 節目エンジン：水平線の生成（表示・スコア・アブレーション用）［賢人 X12・K03、案0］
t 時点で確定済みのスイングだけから毎回生成する。
```
候補点 pts:
  BIG 帳簿の確定スイング j（t-1199 <= j <= t-12）:
     高値 j で H[j] > SMA80[j] → (H[j], 重み1, 高値)      # 4H 20MA の「山」だけ（賢人：20MA の山谷）
     安値 j で L[j] < SMA80[j] → (L[j], 重み1, 安値)      # 「谷」だけ
  D1 帳簿の確定スイング j（t-2879 <= j <= t-72）:
     高値 j で H[j] > SMA480[j] → (H[j], 重み2, 高値)；安値 j で L[j] < SMA480[j] → (L[j], 重み2, 安値)
  （SMA が未計算の点は除く）
tol_lv = TOL_LV(0.6) × ATR[t]
価格の昇順に並べ、先頭から走査: 新クラスタ ⇔ (p - クラスタ先頭) > 2·tol_lv または (p - 直前の点) > tol_lv
節目 = { price: クラスタ内価格の中央値（偶数個は中央2つの平均）, touch: 重みの和,
         nh: 高値の数, nl: 安値の数, d1: D1 の点を含むか }
```
- **エリア判定**（表示）：現在値 ±2×ATR の範囲で touch 最大の節目を基準線にする（同値なら最も近いもの）。現在値が基準線より上なら「買い方優勢」、下なら「売り方優勢」、範囲内に節目がなければ「中立」。

### 6.3 背後の支え（S3・F+support・kenjin_only）［賢人 X01・K04］
B＝押しの極値。買いは min_{k∈W} L[k]、売りは max H。tol_s = TOL_S(1.0)×ATR[t]。次の3種類のうち、存在するものの数を n_sup（0〜3）とする。

| 種類 | 条件 |
|---|---|
| HZ | touch≥2 の節目が \|price−B\|≤tol_s にある |
| FLIP | \|price−B\|≤tol_s の節目で、nh≥1 かつ price<C[t]（旧抵抗を上抜けて戻ってきた、レジサポ転換）。売りは nl≥1 かつ price>C[t] |
| KEY | 押しの起点より前の最新の BIG 安値（BIG.lows(t,4) のうち idx<j_peak の先頭）が \|price−B\|≤tol_s にある |

MA の支えは数えない。G2 がすでに SMA80 への到達を必須にしているので、数えると案0の「8割が通過して選別にならない」問題が再発するからである。

### 6.4 前方の反対勢力と目標（S5・F+clear・oku_only・表示）［100億 要素②・本人X RR1:2／案0の CF 定義］
```
TH_run = max(H[j_peak .. t])            （売り: min(L[j_peak .. t])）  # 現在の波の極値＝「目標」であって反対勢力ではない
CF = { lv.price : lv.price - TH_run > tol_lv かつ 範囲条件 }  ∪  { SMA480[t] : SMA480[t] > price }
     範囲条件  cf_scope=strong（既定）: lv.touch >= CF_MIN_TOUCH(3)  ／  cf_scope=daily: lv.d1 == true
rr_cf = (min(CF) - price) / R            （CF が空なら 99）
目標候補 TG = {TH_run} ∪ {lv.price : lv.touch >= 2 または lv.d1} ∪ {SMA480[t]}  のうち price より先のもの
near_r = (最寄りの TG - price) / R       （TG が空なら 99）
TP1 = (TG - price)/R >= 1.0 を満たす最寄り。なければ price + 2.0R
TP2 = TP1 + tol_lv より先で最寄りの TG（表示用）
```
押しの起点（BH[0]）とその周辺の高値は TH_run 以下なので、反対勢力に数えない。MinCore の藁人形テストはここを数えていたため、それを是正した。

### 6.5 G3：遅すぎ上限（F+G3・mincore_final でのみ使用）
lvl_dist = (SH.p − SMA80[t])·d/ATR[t] > LVL_MAX_ATR(3.0) なら R07。

## 7. トリガー（1H 転換の厳密定義）と注文

### 7.1 1H 転換（買い。売りは鏡像）［共通 C02・C01・C08］
```
SH  = SMALL.highs(t,1)[0]                       # 直近確定の 1H 戻り高値
      SH.idx <= j_peak なら R03（戻り高値が押しの内側にない）
L0  = SMALL.lows(t,6) のうち idx < SH.idx の先頭  # 戻り高値の直前の安値（なければ R03）
runLow = min(L[SH.idx+1 .. t])                  # 戻り高値以降の最安値＝切上げ安値の候補
条件A（安値切上げの維持）: runLow > L0.p          満たさなければ R04
条件B（未消化）: max(C[SH.idx+1 .. t]) <= SH.p    満たさなければ R05（終値で更新済み＝この構造は消化済み）
key = (d, SH.idx)；1セットアップにつき約定1回：key が約定済み集合にあれば R06
```
- 約定の瞬間に「戻り高値以降の安値がすべて底 L0 より上（安値切上げ）」と「価格が戻り高値を上抜け（高値更新）」が同時に成立する。これは、両者の「安値切上げ＋高値更新の確定」を、ブレイクそのもので執行する形である（賢人2019年例「直近高値の直上に買い注文」、100億 STEP4「転換確定の瞬間」）。
- 売りは次のとおり。
  - SH の代わりに SMALL.lows(t,1)[0]（idx>j_peak）を使う。
  - L0 の代わりに、それより前の最新の SMALL 高値 H0 を使う。
  - runHigh=max(H[...])。条件Aは runHigh<H0.p、条件Bは min(C[...])≥SL.p。

### 7.2 注文価格・損切り・R
```
price = SH.p + d × ENTRY_BUF_ATR(0.05) × ATR[t]                       # 逆指値（BUY STOP / SELL STOP）
buf   = max(SL_BUF_ATR(0.2) × ATR[t], 3 × s_nom)                      # スプレッド下限つきバッファ
SL    = runLow - d × buf                                              # 切上げ安値の外［共通 C03］
R     = (price - SL) × d
R < R_MIN_ATR(0.8)×ATR[t] → R09（見送り。底 L0 への退避はしない＝sl_anchor=run）
R > R_MAX_ATR(3.0)×ATR[t] → R10（F+d1soft で rel=-1 のときは 1.5×ATR）
```

### 7.3 待機注文の維持・更新・取消（毎回 H1 足の確定時）
1. 建玉がない、かつ §2.6 の時刻ルールが新規を許すときだけ評価する。
2. d=+1 → d=−1 の順に §8 のゲートを評価する。両方成立したらスコアの高い方を採り、同点なら買い。既定（G1 が排他）では両方は成立しない。
3. 候補がなければ、待機注文を取消す（INVALID）。
4. 候補の key が待機注文と違う、または待機注文がなければ、新規に置く（ARMED を通知）。
5. key が同じなら、price・SL・TP1 を今回の値に置き直す（ATR と runLow の変化を反映する。MT5 では OrderModify）。
6. 有効期限は設けない。取消は構造・時刻・建玉の条件だけで決まる。
7. 1銘柄につき建玉1・待機注文1まで。

### 7.4 約定判定（Python 参照実装＝`fusion/broker.py` と同じ）
- 買い逆指値は、足 k の Ask 高値（H[k]+s/2）≥ price で約定する。約定価格＝max(Ask 始値, price)（窓開けは始値）。売りは Bid 安値（L[k]−s/2）≤ price で、約定価格＝min(Bid 始値, price)。
- 約定した足では損切りの到達だけを判定する。
- 約定した key を約定済み集合に加える。
- R の実績は |約定価格−初期 SL| で記録する（スプレッド込み）。

### 7.5 MT5 での約定・防御
- 発注時に Ask がすでに price 以上なら BUY STOP は拒否されるので、成行で入る。これは Python の「始値約定」と同じ扱い。
- 現在のスプレッドが 3×s_nom を超える間は、その足では武装・修正しない（取消して次の足で評価し直す）。Python は固定スプレッドなので、この規則は発動しない。
- SL バッファは s_nom（入力の固定値）で計算する。実スプレッドは使わない。照合のためである。

4. **約定後**：①と同じ出口（H1 の BIG 安値トレール、週末・休場決済）。
5. **優先順位**：①＞①-M15＞②。上位の注文が成立したら、下位の待機注文を置き換える。
6. **M15 で回すときの注意**：M15 を有効にすると、①の約定と損切りの判定も M15 足で行う。そのため H1 単独で回した場合と数件ずれうる。

### 11.3 パターン③：日足波の押し × 4H 終了兆候 × 1H 転換（H1 だけで可能。既定 OFF）［100億 パターン③・④-A］

    pre-compute: ATR, SMA20/80/480, books SMALL/BIG/D1, dow_machine(T_SMALL,T_BIG,T_D1),

        if best is None: pend = None; continue                         # INVALID

## 17. MQL5 実装注記（Python と差が出やすい箇所）
1. **時間足**：既定経路は PERIOD_H1 の系列だけを使う（CopyRates／iMA／iATR、shift≥1）。②と①-M15 だけが PERIOD_M15 を使い、H1 の確定判定は Python の closed_index_map と同じ「H1 の確定時刻≤M15 の確定時刻」にする。
2. **インデックス**：Python の足 idx と MQL5 の shift の関係は shift＝t−idx＋1（shift 0 は未確定）。スイングの「j≤t−N」は「shift≥N+1」に当たる。
3. **履歴**：帳簿は 400/3000/8000本を使う。チャートの最大バー数は10000以上にし、テスターでは開始日の前に H1 10000本以上を読み込む。持続型ダウ状態機械は OnInit で履歴の先頭から再生する。照合は、最初の転換イベントより後の期間で行う。
4. **フラクタルの不等号**：新しい側は厳密、古い側は非厳密。新しい確定足ごとに j=t−N を判定して帳簿に追加する増分方式で実装する。
5. **逆指値**
   - 毎 H1 で price と SL が変わる（ATR と runLow が動くため）ので、OrderModify する。
   - STOPS_LEVEL や FREEZE_LEVEL で拒否されたら、前の注文を残して次の足で再試行し、ログに残す。
   - ORDER_TIME_SPECIFIED が使えないブローカーでは GTC で置き、取消は EA が行う。
   - 発注時に Ask がすでに price 以上なら成行で入る（§7.5）。
6. **価格の丸め**：NormalizeDouble はサーバーに送る価格にだけ使い、判定は生の double で行う。境界（runLow>L0、R の上下限、depth≤0.5 など）では 1e−10 程度の差で判定が割れうる。照合で差が出たら、まず境界値を確認する。
7. **SL の修正**：トレールでは「new_SL<現在 Bid−stops_level」を Python と MQL5 の両方の条件に加えると一致する。
8. **時刻**：判定は iTime(PERIOD_H1,1)+3600（確定時刻）で行い、TimeCurrent は使わない。サーバー時間が NY+7 でないブローカーでは、入力 InpServerOffset で時刻ルールを換算する。暦のリスト（CAL_CLOSED／CAL_EARLY、XAU の Good Friday 計算）は Python と同じものを使う。
9. **休場明け**：前の確定足の終了から新しい足の開始まで12時間以上空いたら、最初のティックで成行決済する。Python ではその足の始値で決済する。
10. **スプレッド**：Python は s_nom で固定する。MT5 テスターで照合するときは固定スプレッドを使う。実スプレッドでの成績は別に報告する。スプレッド防御（3×s_nom 超）は MT5 だけで発動する。
11. **約定順序**：Python は足の中の順序が分からないので SL を優先し、約定足では SL だけを判定する。MT5 のリアルティックは実際の順序で約定するので、MT5 の方が良い成績になる方向に差が出る。
12. **欠損足**：MT5 はティックのない時間の足を作らない。Python も resample の dropna で除くので、扱いは同じ。祝日の薄い足で差が出ることがある。
13. **部分決済**：既定にはないので、最小ロットの丸め問題は出ない。F+partial／oku_only で使う場合は、VOLUME_STEP で切り捨て、2分割できないときは全量決済してログに残す。
14. **複数銘柄**：銘柄ごとに新しい足を検出し、銘柄ごとに独立した状態（帳簿・状態機械・約定済み集合）を持つ。

## 21. 検証計画と合格基準（事前登録）
実行の細則（データの作り方、プールの境界、統計の定義、素朴ベースラインの校正手順）と、設計段階で起きたプロトコル逸脱の記録は `fusion/PREREGISTRATION.md` にある。

### 目的
凍結した fusion v1.0 に実データ上の優位性があるかを1回だけ判定する。あわせて、oku_only・kenjin_only・mincore_final との比較と、各要素の寄与を測る。

### 原則
- 既定構成とパラメータは本仕様で凍結する。OOS の結果を見て数値や構成を変えない。
- 変更する場合は v1.1 として事前登録し直し、さらに新しい未接触データで評価する。
- 一度出した OOS は、良くても悪くてもそのまま報告する。

### 段階0 凍結と事前登録
- git にコミットするもの：本仕様、参照実装（`fusion/strategy.py` に移植）、VARIANTS 一覧、照合表（§18）、ゴールデン CSV、評価スクリプト、合格基準（本 test_plan）。ハッシュを記録する。
- 評価スクリプトは、登録済みの全変種を一括で走らせて一括で出力する。一部だけを先に見ない。

### 段階1 実装の受入れ（回数だけ。損益は見ない）
- 照合表の各欄が ±5% 以内であること。
- ゴールデン CSV が完全一致すること（BT2017 は18件、OANDA EURUSD IS は136件）。
- 切断テストに合格すること（2016-01-01 で切り、2015-11 より前の76件が一致）。
- 理由コード別のファネル件数が一致すること。
- MQL5 は、MT5 で書き出した H1 足に対して Python と照合する（回数 ±5%、エントリー時刻±1本で方向一致90%以上、初期SLの差1ポイント以内）。

### 段階2 IS 診断（既知データ。2013〜2017、4銘柄）

- 既知のホールドアウト（2010〜2012、4銘柄。AUDUSD/USDCAD 2013〜2017）も参考として再計算し、併記する。

### 段階3 最終 OOS（1回だけ）
データは OANDA 1分足（FutureSharks/financial-data）から H1 と M15 に変換し、サーバー時間（NY+7）、土日足除外で作る。指標のウォームアップには直前データを使うが、取引は評価期間に入ったものだけを数える。

- ②と①-M15 降格は、M15 データがある U-A・U-B で副次的に評価する。

### 合格基準（fusion。P1〜P6 をすべて満たして「合格」）
- P1：合算の平均R>0 かつ t≥2.0。月単位のブロック・ブートストラップ（1万回）による平均Rの95%区間の下限が0より大きい。
- P2：U-A・U-B・U-C のうち2つ以上で平均R>0。30回以上ある銘柄の60%以上で平均R>0。
- P3：前半と後半の安定性。各プールを期間の中点で前半・後半に分けて合算し、どちらも平均R>0。
- P4：エントリーの付加価値。fusion の平均R が、素朴ベースラインの20シード平均＋0.10R 以上で、かつシード分布の95パーセンタイルを上回る。
- P5：外れ値への頑健性。R の上位1%の取引を除いても合算平均R≥0。
- P6：DSR（Deflated Sharpe Ratio。月次R系列、試行数 N=250 は全設計・審査の IS 試行の保守的な総数、試行間の SR 分散は IS 全変種から推定）≥0.90。
- 警告（不合格ではないが、自動売買の前に解消が必要）：
  - 買いと売りの片方だけがマイナス（方向・レジーム依存）
  - GAP_FALLBACK が FX で年1件を超える（暦の不備）
  - EURUSD の10か月あたり回数が15回未満

### 比較（fusion は oku_only・kenjin_only に勝つか）
- 両方を満たせば「fusion の勝ち」とする。
  - 銘柄年あたりの総Rの差が正で、その90%ブートストラップ区間が0を含まない
  - 平均Rの差の90%区間の下限が −0.10R より大きい（1回あたりの質で明確に劣らない）
- mincore_final との比較も同じ方法で行い、IS 選択の寄与（楽観バイアス）を推定する。
- oku_only・kenjin_only は厳選しすぎで回数が少ない（OOS 合算で約290回・400回の見込み）ため、区間が広いことを前提に報告する。

### アブレーションの判定
- 各変種と fusion の差 Δ平均R を、SE_Δ=√(SE_v²+SE_f²) で評価する（共通取引があるので保守的）。
- 判定はプール別・銘柄別の符号と合わせて行う。「有意」と言うときは Holm 補正をかける。
- 結果は v1.1 の候補として記録するだけで、v1.0 の既定は変えない。

### 追加データ（複数年・複数通貨）
- histdata の M1（EURUSD・USDJPY・XAUUSD）が取れた場合は、2021年以降の H1・M15 で fusion・②・①-M15 を同じ基準で確認する（U-D）。
- 最後に、ユーザーの MT5 ストラテジーテスターで、ブローカーのデータ（EURUSD・USDJPY・GBPUSD・XAUUSD、2021-01〜最新、開始前に H1 10000本以上の履歴）を使って確認する。
  - リアルティック・固定スプレッドで Python との照合を取り、そのうえで実スプレッドでの成績を別に報告する。

### 報告に必須の項目
- 回数、勝率、総R、平均R（95%区間）、PF、最大DD(R)、最大連敗
- 銘柄別、売買別、年別、プール別、前半・後半別、決済理由別
- グレード別、S1〜S6 の層別、rel 別、n_sup 別

- mincore_final と既知ホールドアウトの併記
- EURUSD の10か月あたり回数と、BT 同梱ファイル全体（2018-02 まで）の回数

### 判定後の扱い
- 合格：U-D／MT5 の確認と、デモでのフォワード3か月（通知のみ、30シグナル以上、Python との一致を確認）を経た後に、自動売買を任意で有効にできる（risk 0.5% から）。
- 不合格：v1.0 は「優位性なし」と記録する。自動売買は無効のまま、シナリオ・パネルの道具（裁量の補助）としてだけ使う。改良は v1.1 として事前登録し、未使用データで1回だけ評価する。
